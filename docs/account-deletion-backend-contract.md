# Удаление аккаунта: контракт для бэка

Клиентский контракт сборки Quizice 1.0 (3), 2026-10-23. Реализация, миграции и деплой бэка в этот PR не входят. Проверенная 2026-10-23 публичная OpenAPI-схема production содержала 25 путей; метода удаления и поля `recreateDeletedAccount` в ней не было. Production-аккаунты при проверке не удалялись.

## Удаление и повтор запроса

```http
DELETE /api/v1/me/account
X-Quizice-Authorization: Bearer <existing access token>
X-Idempotency-Key: <UUID>
Accept: application/json
```

Тела запроса нет. Аккаунт определяется исключительно токеном. Специальный заголовок авторизации нужен для существующей конфигурации Yandex Serverless Containers; необходимо сохранить строгую проверку неоднозначных заголовков.

Только **204 No Content** после коммита транзакции подтверждает удаление. Клиент не принимает 200, 202 или 401 за успех. Он сохраняет ключ операции и исходный токен для повтора после таймаута или перезапуска, блокируя обычную авторизацию до разрешения неоднозначного результата.

В той же транзакции сохранить минимальное подтверждение операции: ключ, защищённый digest исходного токена и время завершения. Проверять его **до** обычной зависимости `CurrentUser`: после удаления токен уже отозван, но повтор с тем же ключом и токеном обязан вернуть 204. Одного ключа недостаточно для авторизации. Не хранить и не логировать токен открытым текстом. Подтверждение не должно каскадно удаляться с аккаунтом.

Повтор старой операции после создания нового аккаунта должен только подтвердить старое удаление, не затрагивая новый UUID. Конкурентные одинаковые запросы выполняют одну операцию. При сбое откатываются данные, подтверждение и отметка удалённой личности вместе.

До согласования срока хранения с клиентом нельзя автоматически удалять подтверждения так, чтобы сохранённый незавершённый запрос потерял возможность безопасного повтора. Ответ 401 без подходящего подтверждения не означает удаление. При первом 401 клиент обновляет обычную Game Center-сессию без разрешения на повторное создание; после неоднозначного предыдущего запроса сохраняет pending-состояние.

Ошибки используют существующий envelope `{code, message, requestId}`: 401 `unauthorized`, 422 `validation_failed`, 409 `idempotency_conflict`, 503 `account_deletion_unavailable`. Для неизвестного токена нельзя раскрывать чужие операции. Отсутствующий маршрут/метод (404/405) не должен менять данные. Возвращать `Cache-Control: no-store`.

## Что удалить одной транзакцией

| Данные | Таблицы / ключ |
| --- | --- |
| Аккаунт и все сессии | `app_user`, `access_token`, UUID пользователя |
| Прогресс, ответы, избранное | `user_question_progress`, `question_answer_event`, `user_theme_preference`, все локали |
| AI-квоты | `ai_monthly_usage`, все месяцы |
| Статистика — требуется явное удаление | `statistics_summary`, `statistics_mode_summary`, `completion_record`, `legacy_statistics_migration`, по `team_player_id` |

У четырёх таблиц статистики нет каскадной связи с `app_user`; удаления одной строки пользователя недостаточно. Проверить существующие каскады остальных таблиц. Не затрагивать каталог, администраторов, другие аккаунты и общий журнал защиты подписей от повторов `game_center_replay`.

## Не допустить восстановления данных поздними запросами

Middleware проверяет токен раньше транзакции сервиса. Поэтому каждый защищённый mutator должен заново заблокировать и проверить существование **того же UUID** внутри своей транзакции.

- `StatisticsService.sync`: принимать UUID авторизованного пользователя вместо одного `team_player_id`, требовать найденную строку `FOR UPDATE`, получать Game Center ID из неё. Старый запрос не должен найти новый аккаунт по тому же Game Center ID.
- `ThemePreferencesService.replace` и `QuestionProgressService`: проверять результат блокирующего запроса; отсутствующий пользователь означает отказ до изменений, включая пустые обновления.
- `AIQuotaService.reserve`: синхронизировать удаление с существующим advisory lock квот, проверять актуальный UUID под блокировкой. Генерация должна завершиться или отмениться до коммита удаления и не восстанавливать квоты позднее.
- Авторизация и удаление используют общий advisory lock Game Center-личности. Порядок нескольких блокировок: **identity advisory lock → AI quota advisory lock → user row lock**. После ожидания повторно проверить владельца токена. Ограничить время ожидания без частичного удаления.

## Создание нового аккаунта только по явному действию

Обычная Game Center-авторизация сейчас создаёт отсутствующего пользователя. После удаления это позволило бы второму устройству или старому клиенту восстановить аккаунт автоматически.

Добавить минимальную отметку удалённой личности на основе HMAC нормализованного Game Center ID с серверным ключом. Указать назначение и фактическое хранение этой отметки в политике, предусмотреть ротацию ключа. Она отличается от подтверждения удаления.

Расширить строгую модель запроса `POST /api/v1/auth/game-center` необязательным boolean-полем `recreateDeletedAccount`:

| Состояние | Поле отсутствует / false | true |
| --- | --- | --- |
| Существующий аккаунт | Обычная авторизация | Обычная авторизация, без сброса |
| Личность никогда не регистрировалась | Первое создание | Первое создание |
| Удалённая личность без действующего аккаунта | **409 `account_deleted`**, без аккаунта и токена | Новый UUID, пустые данные, новая сессия |

Envelope ответа 409 содержит точный код `account_deleted`, безопасное сообщение и `requestId`. Клиент очищает локальные данные после этого подтверждения удаления на другом устройстве. Поле true отправляется только после подтверждения «Создать новый аккаунт». Проверка Game Center-подписи и защита от её повторного использования сохраняются во всех ветках.

## Проверки и порядок выпуска

1. Добавить route/service, DTO, миграции подтверждений/отметок и проверки mutator-ов. Не включать это изменение только на уровне UI.
2. Проверить настоящий router/middleware и PostgreSQL: полную очистку одного аккаунта при сохранении другого; неверную авторизацию; повтор с отозванным токеном; потерю ответа; атомарный rollback; конкурентное удаление; старые запросы после удаления и создания нового аккаунта; запрет автоматической авторизации; явное создание пустого UUID. Моки и SQLite не подтверждают корректность PostgreSQL-блокировок.
3. Определить фактическую обработку журналов, резервных копий, AppMetrica и технических подтверждений. Уточнить политику перед деплоем; не обещать немедленное стирание всех данных провайдеров.
4. Применить миграции, развернуть бэк и пройти полный сценарий на отдельном тестовом аккаунте, включая старую сессию на другом устройстве и работу гостевых викторин.
5. Только после этого нажимать финальную кнопку App Store Review. Статус черновика «Готово к проверке» подтверждает заполнение App Store Connect, но не работоспособность серверного удаления.

Существующие серверные наборы для расширения: `tests/contract/test_player_authorization.py`, `tests/contract/test_auth.py`, `tests/contract/test_statistics.py`, `tests/integration/test_auth_statistics_postgres.py`, `tests/integration/test_ai_quota.py`. PostgreSQL-проверки должны выполняться, а не молча пропускаться в CI.
