# Переключатель предупреждения о задержках ИИ в админке

Это план следующей задачи. **Код переключателя в админке и хранение настройки в БД пока не реализованы.** iOS-контракт уже поддержан подготовленными изменениями. Текущая backend-реализация с `AI_GENERATION_DELAY_NOTICE_ENABLED`, читаемым при старте процесса, есть локально; в рамках этой работы она не задеплоена и предупреждение в production не включалось. Исходное поведение и результаты проверки описаны в [ai-generation-status.md](ai-generation-status.md).

После выполнения этого плана superadmin сможет включать и выключать предупреждение из Quizice Admin. Обычное переключение не требует деплоя, рестарта backend или нового выпуска iOS. Нужен ровно один переключатель; редактор текстов, автоматическая оценка состояния провайдера и общий механизм feature flags в задачу не входят.

В путях ниже `Quizice-backend/…`, `Quizice-admin/…` и `Quizice/…` обозначают корни трёх репозиториев. Новые имена файлов помечены явно. Указанные существующие файлы и паттерны проверены 24 октября 2026; перед реализацией нужно проверить актуальные ветки и голову миграций.

## 1. Источник состояния и модель хранения

Хранить настройку в PostgreSQL, общем для всех экземпляров **одного окружения**. Production и staging не должны делить эту строку. Создать отдельную таблицу `ai_generation_settings` с единственной записью:

| Поле | Тип и ограничения | Назначение |
|---|---|---|
| `id` | integer, PK, `CHECK (id = 1)` | Идентификатор единственной настройки |
| `delay_notice_enabled` | boolean, NOT NULL | Показывать предупреждение |
| `version` | integer, NOT NULL, `CHECK (version >= 1)` | Защита от перезаписи чужих изменений |
| `updated_at` | timestamptz, NOT NULL | Время последнего изменения в UTC |
| `updated_by_admin_id` | UUID, nullable FK → `admin_user.id`, `ON DELETE SET NULL` | Автор изменения; null для начального состояния |

Миграция создаёт строку `id=1`, `delay_notice_enabled=false`, `version=1`, с текущим временем БД и пустым автором. Начальный `false` соответствует текущей подготовленной реализации. Миграция не должна читать случайное окружение CI и переписывать уже существующую настройку при последующих релизах. Если до выполнения этой задачи ENV-вариант успеет выйти и будет включён, перед переключением трафика нужно отдельно перенести его действующее значение в новую строку с аудитом; не выключать предупреждение незаметно.

После появления строки **значение в БД является основным**. `AI_GENERATION_DELAY_NOTICE_ENABLED` сохраняется как аварийное резервное значение для публичного endpoint при недоступности БД; значение по умолчанию — `false`. Оно по-прежнему читается при старте, одинаково задаётся всем экземплярам и не меняется из админки. ENV не перекрывает доступную запись в БД и не становится вторым обычным способом управления.

Не хранить рабочее значение в глобальной переменной процесса, словаре Python, локальном JSON, памяти конкретного воркера или `localStorage` админки. Не добавлять бессрочный кеш последнего успешного чтения. Обычный запрос после успешного сохранения должен читать уже зафиксированное значение с основной БД независимо от того, на какой экземпляр backend он попал.

## 2. Контракт административного API

Добавить маршруты в существующий `Quizice-backend/src/quizice/api/admin.py`. Использовать его `AdminBearer`, `require_admin`, `viewer`, `superadmin`, `_client_ip` и `current_request_id()`. Пользовательский Game Center/bearer-токен не предоставляет административных прав.

| Операция | viewer | editor | superadmin |
|---|---|---|---|
| `GET /api/v1/admin/ai-generation-settings` | Да | Да | Да |
| `PUT /api/v1/admin/ai-generation-settings` | 403 | 403 | Да |

Все ответы административных маршрутов — `Cache-Control: no-store`. DTO наследуются от существующего `AdminModel` в `Quizice-backend/src/quizice/models/admin.py`: camelCase, строгие типы, запрет лишних полей. Не вводить отдельную авторизацию или новый формат ошибок.

### Чтение

```http
GET /api/v1/admin/ai-generation-settings
Authorization: Bearer <admin-session>
```

```json
{
  "delayNoticeEnabled": false,
  "version": 1,
  "updatedAt": "2026-10-24T19:00:00Z",
  "updatedByAdminId": null
}
```

GET возвращает фактическую запись БД. Если БД недоступна или строка отсутствует, вернуть 503 с кодом `ai_settings_unavailable`, а не показывать ENV как якобы сохранённую настройку. Отсутствие строки после успешной миграции — неисправность, требующая диагностики; публичный endpoint при этом использует fallback.

### Сохранение

```http
PUT /api/v1/admin/ai-generation-settings
Authorization: Bearer <admin-session>
Content-Type: application/json
```

```json
{"delayNoticeEnabled":true,"version":1}
```

Успешный ответ — 200 и полная актуальная запись:

```json
{
  "delayNoticeEnabled": true,
  "version": 2,
  "updatedAt": "2026-10-24T19:02:00Z",
  "updatedByAdminId": "00000000-0000-4000-8000-000000000001"
}
```

`version` в запросе — версия, полученная последним GET. При несовпадении вернуть стандартный envelope с HTTP 409, `code: "conflict"`, `requestId` и понятным сообщением. По образцу `AdminService.update_question()` использовать `AdminConflict` → HTTP 409. Не выполнять молчаливое сохранение поверх новой версии.

В одной транзакции выполнить `SELECT … FOR UPDATE` строки `id=1`, проверить версию, изменить значение, увеличить версию на 1, записать время/автора и добавить событие аудита. Вернуть успех только после успешного commit. Альтернатива — условный `UPDATE … WHERE version=:expected RETURNING …`, если аудит остаётся атомарным; выбрать один подход, существующий код использует блокировку строки.

Если версия совпала, а значение уже равно запрошенному, вернуть текущую запись без увеличения версии и без повторного события изменения. Сначала всегда проверяется версия: устаревший запрос получает 409 даже при совпадении желаемого значения. Два разных изменения с одной версией не могут оба завершиться успешно.

Ошибки: 401 без действующей admin-сессии; 403 для записи от viewer/editor; 422 при отсутствующих/лишних полях, строке вместо bool или некорректной версии; 409 при конфликте; 503 при недоступном хранилище. Формат берётся из `Quizice-backend/src/quizice/api/errors.py`; внутренние SQL/DSN/исключения клиенту не возвращать. Для 503 использовать доменный `APIError` с `ai_settings_unavailable`, не ошибку провайдера генерации.

### Аудит

Использовать `add_admin_audit()` из `Quizice-backend/src/quizice/services/admin_auth.py` и существующий `AdminAuditRecord`. Запись настройки и событие должны либо сохраниться вместе, либо оба откатиться.

- `action`: `ai_generation_notice.updated`;
- `resource_type`: `ai_generation_settings`, `resource_id`: `1`;
- существующие `admin_id`, `actor_email`, `request_id`, `ip_address`, `created_at`;
- `details`: `{"before":{"delayNoticeEnabled":false,"version":1},"after":{"delayNoticeEnabled":true,"version":2}}`.

GET, отклонённый запрос, конфликт, повторное сохранение без изменения и неуспешный commit не создают события успешного изменения. Токены, AI-ключи и заголовки авторизации в аудит не включать.

## 3. Публичный endpoint и отказоустойчивость

Сохранить внешний контракт `GET /api/v1/ai/status?locale=ru` без новых обязательных полей:

```json
{"locale":"ru","notice":null}
```

```json
{"locale":"ru","notice":"Сейчас вопросы создаются с задержкой. Это может занять больше времени, чем обычно."}
```

`locale` обязателен; использовать существующий `SupportedLocale` и стандартный 422 `unsupported_locale`. Сохранить `Cache-Control: no-store`, отсутствие ETag, отсутствие требования пользовательской авторизации и обход разрешения bearer-токена в `Quizice-backend/src/quizice/api/bearer.py`, в том числе для устаревшего токена и завершающего `/`. AI-ключ, вызов AI Studio и квота генерации для получения статуса не нужны.

**После этого изменения endpoint уже не будет полностью независим от БД.** Нужно исправить старое обещание в README, docstring `Quizice-backend/src/quizice/api/ai_status.py`, соответствующих тестах и `Quizice/docs/ai-generation-status.md`. Новое обещание: штатное состояние читается из БД, но её неисправность не должна превращать необязательную подсказку в длительное ожидание или блокировку создания вопросов.

Предлагаемый алгоритм каждого публичного GET:

1. После проверки locale запустить одно короткое чтение булевого поля по PK с основной БД, без `FOR UPDATE`, без повторных попыток и без записи.
2. Дать этому чтению общий бюджет около **200 мс**, включая ожидание соединения, подключение/проверку соединения и выполнение запроса. Один `statement_timeout` не покрывает ожидание пула: нужен общий асинхронный deadline. Настроить драйверный/серверный timeout внутри этого бюджета. Использовать отдельную короткую сессию, корректно отменить запрос, откатить/закрыть её; не оставлять фоновые запросы и занятые соединения после fallback. Проверить фактическую длительность отмены: `asyncio.timeout()` сам по себе не гарантирует мгновенное завершение cleanup драйвера.
3. При успешном чтении использовать значение БД. При timeout, недоступности соединения, отсутствующей таблице/строке использовать стартовый `AIGenerationSettings.delay_notice_enabled` и вернуть обычный 200 с тем же JSON. Отмену самого HTTP-запроса не поглощать. Не ловить без разбора все ошибки программирования.
4. Выбрать существующую локализованную строку либо `null`. Не отдавать клиенту SQL-состояние или подробности fallback.

Для первой реализации не нужен кеш: чтение одного bool выполняется при открытии карточки, а не во время каждого шага генерации. Не запускать опрос в фоне. Использовать ограничение конкурентности чтений без длинной очереди; при насыщении лимита сразу fallback. Если общий пул БД при нагрузочном тесте мешает основным маршрутам, выделить маленький ограниченный пул для чтения этой настройки с тем же общим бюджетом и закрытием в lifespan. Не считать увеличение общего пула исправлением отсутствующего deadline.

Нормальный POST генерации не должен вызывать этот status endpoint, ждать настройки или менять поведение по её значению. Предупреждение не отключает генерацию и не влияет на квоты. iOS уже выполняет запрос статуса независимо, скрывает подсказку при ошибке и получает новое значение при следующем открытии карточки/смене языка; мгновенное обновление уже открытой карточки без нового запроса в задачу не входит.

Добавить безопасное структурированное событие/счётчик fallback с причиной (`timeout`, `database_unavailable`, `missing_setting`) и длительностью чтения, без повторной записи ошибки в ту же недоступную БД. Ограничить частоту однотипных warning-логов. Тесты должны проверять отсутствие утечек сессий и задач после серии timeout.

Во время аварии резервное ENV-значение может отличаться от последнего сохранённого значения БД. Это явный компромисс: предпочтение отдаётся быстрой необязательной подсказке. Экземпляры с доступной БД могут временно отвечать иначе, чем экземпляры в fallback; обещание полного совпадения при частичном сетевом отказе было бы неверным. После восстановления очередной GET снова использует БД, без рестарта и без ожидания истечения кеша. Для всех активных ревизий держать одинаковый ENV-fallback.

## 4. Порядок реализации backend

1. В новом `Quizice-backend/src/quizice/models/ai_generation_settings.py` описать ORM-модель единственной записи; зарегистрировать модуль в `Quizice-backend/src/quizice/models/orm.py`, чтобы Alembic и проверка схемы видели таблицу.
2. Добавить Alembic-миграцию `Quizice-backend/alembic/versions/<revision>_add_ai_generation_settings.py`. Выбрать фактическую текущую единственную голову; на момент проверки это `d8e4a1000003`, не фиксировать её вслепую после изменений других задач. Обновить `REQUIRED_ALEMBIC_REVISION` в `Quizice-backend/scripts/deploy-yc.sh` на новую голову и связанные проверки готовности/реестра ORM.
3. В `Quizice-backend/src/quizice/models/admin.py` добавить `AdminAIGenerationSettings` и `AdminAIGenerationSettingsUpdate` на основе `AdminModel`; DTO публичного endpoint в `Quizice-backend/src/quizice/models/ai_status.py` не менять.
4. В новом `Quizice-backend/src/quizice/services/ai_generation_settings.py` реализовать чтение и транзакционное изменение с проверкой версии и аудитом. Использовать существующие `AdminConflict` и `add_admin_audit`, не копировать auth-систему. Передавать зависимости явно, чтобы deadline/fallback можно было тестировать без реальной сети.
5. Добавить GET/PUT в существующий `Quizice-backend/src/quizice/api/admin.py`, привязав GET к `viewer`, PUT к `superadmin`; административные операции при сбое БД не сохраняют ничего в ENV/памяти.
6. В `Quizice-backend/src/quizice/api/ai_status.py` заменить прямое чтение флага на ограниченное чтение сервиса с fallback; подключить зависимости через `Quizice-backend/src/quizice/main.py`. Сохранить исключение из player-auth lookup и все публичные поля/переводы.
7. Уточнить комментарии в `Quizice-backend/src/quizice/config.py`, `.env.example`, README и документации: ENV теперь только fallback/default. Сохранить прокидывание ENV в `docker-compose.yml`, `scripts/deploy-yc.sh` и `.github/workflows/backend-ci.yml`; обычное сохранение через админку не должно менять эти файлы, создавать ревизию или запускать webhook деплоя.

Добавить отдельную страницу `/ai-generation` с названием **«Генерация ИИ»**. Она доступна всем трём существующим ролям для чтения; viewer/editor видят состояние и объяснение «Изменять настройку может только суперадминистратор». Изменять флаг может только superadmin; серверная проверка обязательна независимо от скрытой кнопки.

| Файл в Quizice-admin | Изменение |
|---|---|
| `src/types.ts` | Типы `AIGenerationSettings` и `AIGenerationSettingsUpdate` с полями контракта выше |
| `src/api/client.ts` | `aiGenerationSettings(signal?)` → GET `/ai-generation-settings`; `updateAIGenerationSettings(input)` → PUT того же пути через существующий `request<T>` |
| `src/pages/AIGenerationPage.tsx` — новый | Чтение, форма переключателя, сохранение и все состояния |

| `src/components/AppLayout.tsx` | Пункт `navItems` «Генерация ИИ», иконка из используемого `lucide-react`, доступ всем admin-ролям; существующий механизм обновит title и мобильное меню |

| `src/test/fixtures.ts`, `src/test/renderApp.tsx` | Fixture новой записи и дефолтные mock API-методы |

`src/api/client.ts` уже обрабатывает admin bearer, отмену запросов при смене сессии, timeout, `ApiError` и глобальный выход при 401. Использовать его, а не отдельный `fetch`/токен. `src/auth/AuthProvider.tsx` уже очищает React Query cache при выходе; сохранить это поведение.

Страница использует существующие `useQuery`, `useMutation`, `useQueryClient`, `useAuth`, `useToast`, `PageHeader`, `LoadingState`, `ErrorState`, `Field`, `Button` и `formatDate`. Query key, например `['ai-generation-settings', admin.id]`; GET поддерживает `AbortSignal`. Для мутации выключить автоматические повторы.

Форма содержит один доступный с клавиатуры checkbox/switch **«Показывать предупреждение о задержках»**, пояснение «Пользователи увидят сообщение при следующем открытии карточки создания с ИИ», статичный русский пример сообщения, время последнего сохранения и кнопку **«Сохранить»**. Отдельного подтверждающего диалога для этого обратимого изменения не требуется. Не показывать пользователю админки технические идентификаторы пула, ENV и миграции в основном сценарии.

Поведение:

- До успешного GET — loading; не показывать `false` как полученное состояние. Ошибка GET — `ErrorState` с повтором, форма недоступна.
- Держать отдельно сохранённые данные и черновик. Переключение меняет только черновик; запрос уходит по кнопке «Сохранить». Кнопка выключена без изменений, для viewer/editor и во время запроса; при сохранении показывается loading.
- Отправлять версию сохранённой записи. Успешный PUT заменяет данные в query cache и черновик полным ответом сервера, затем показывает «Настройка сохранена». Не подтверждать успех до ответа и не использовать оптимистическое отображение как уже сохранённое.
- Если фоновый refetch обнаружил новую версию, не перезаписывать незаметно несохранённый черновик. Показать конфликт/предложение загрузить актуальное состояние.
- При 409 выполнить GET, показать актуальное состояние и сообщение «Настройку изменил другой администратор. Проверьте новое значение и сохраните снова». Не повторять PUT автоматически с новой версией. Сохранённый пользовательский выбор можно оставить видимым как несохранённый, но следующий PUT должен быть новым осознанным нажатием.
- При сетевом timeout результат PUT неизвестен: сервер мог успеть commit. Показать «Не удалось подтвердить сохранение» и перечитать GET. Не выдавать «не сохранено» как установленный факт и не повторять PUT вслепую. Сверить полученные значение/версию и позволить пользователю принять дальнейшее решение.
- При 403 сделать форму недоступной, обновить данные текущего администратора/роль; при 401 использовать существующий выход. Запоздалый ответ предыдущей сессии не должен менять страницу новой сессии.
- При прочей ошибке сохранить черновик и показать ошибку; не прятать существующее сохранённое состояние. Screen reader должен получать изменение статуса сохранения/ошибки, switch — иметь связанный label и понятное состояние.

## 6. Тесты и проверка

Новые тесты должны проверять реальные последствия изменения, особенно конкуренцию и отказ БД. Старые утверждения «status вообще не открывает DB session» необходимо заменить: теперь не должно быть **auth lookup** или AI-вызова, но ожидается одно короткое чтение настройки.

Backend:

- Два отдельных приложения/пула с одной тестовой БД: PUT через A, последующий GET статуса через B видит новое значение без рестарта; новый процесс видит то же состояние. ENV `false` при БД `true` и ENV `true` при БД `false` подтверждают приоритет БД.

Это критерий работы приложения в контролируемом тесте, не обещание сетевой задержки production. Отдельно измерить acquire/query/cleanup под конкуренцией и подтвердить, что status не задерживает генерацию из-за исчерпания общего пула.

## 7. Порядок выпуска и приёмка

1. Реализовать и проверить backend: аддитивная миграция, новая модель/сервис/admin API, bounded read публичного endpoint. Начальное значение `false`; проверить, не появился ли к этому моменту включённый ENV-вариант, и при необходимости сохранить его состояние при переходе.
2. Выпустить backend штатным процессом `Quizice-backend/scripts/deploy-yc.sh` с проверкой миграций/readiness. Не обходить существующие процедуры публикации. Сначала завершить переход всех обслуживающих запросы экземпляров на DB-вариант: старая ENV-ревизия игнорирует изменения из админки и при смешанном трафике даёт расходящиеся ответы.
3. Проверить новые admin GET/PUT и публичный status в staging, включая два экземпляра, конфликт версии и аварийный fallback. Затем выпустить Quizice Admin с новой страницей. Frontend не выпускать первым: новый экран иначе получит 404 старого backend.
4. Подготовленный iOS-контракт из этой задачи совместим с обоими вариантами backend. Если его первоначальный выпуск ещё не состоялся, выполнить его отдельно; в дальнейшем для переключений обновление iOS не требуется. Приложение с поддержкой контракта получает состояние при открытии карточки.
5. После выпуска проверить контролируемое on/off через админку: PUT меняет строку и аудит, public GET выдаёт соответствующий текст/null, повторное открытие карточки отображает результат. Проверить, что при этом не создана новая ревизия контейнера и не вызван deployment webhook.
6. Обновить `Quizice/docs/ai-generation-status.md` и backend README, явно заменив обычное управление через ENV на админку и описав DB/fallback. Настоящий документ оставить как ТЗ либо отметить выполненные пункты после реализации; сейчас они не выполнены.

Готово, когда настройка переживает рестарт и смену экземпляра; доступна всем admin-ролям для просмотра, меняется только superadmin; не теряет параллельные изменения; фиксируется атомарно с аудитом; public/iOS-контракт и все шесть текстов сохранены; сбой БД приводит к ограниченному по времени fallback, а не блокировке генерации; обычный toggle не требует деплоя.

Для отката frontend достаточно убрать новый экран, состояние остаётся в БД. При откате backend на старую ENV-реализацию сначала согласовать ENV с текущим значением БД и закрыть запись из админки, иначе старый backend начнёт отвечать другим состоянием. Не удалять таблицу и аудит при обычном откате приложения.
